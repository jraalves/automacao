Como o reprocessamento funciona no desenho real

  • A API marca a tentativa e devolve o documento para a fila; o worker consome de novo com backoff exponencial.
  • Falha definitiva vai para um beco sem saída com motivo — é ela que entra no SLI de taxa de erro do worker.
  • Reprocessar nunca regrava por cima de um arquivo publicado: a chave é empresa + tipo + número demo, e o destino é verificado por ETag.
  • Cada reprocessamento gera um novo span no mesmo trace_id, o que permite contar tentativas sem perder o histórico.

O botão Reprocessar desta página não faz nada disso: ele apenas move o item no estado local para você ver o fluxo. Nenhuma chamada de rede é feita.

O que mudou do original para este desenho

  • O caso original era React + Python/FastAPI + MongoDB rodando em contêineres; a UI, a API e o worker de extração são os mesmos três papéis deste diagrama.
  • A evolução para contêineres e orquestração adicionou: leitura de configuração por ambiente, sondagens, e a separação API/worker que você vê aqui.
  • A camada de borda (Ingress + proxy de autenticação) e a observabilidade OTLP fazem parte do desenho documentado desta demonstração, não de uma versão executada.
  • Nomes de produto, domínio e tenant do ambiente original foram substituídos por descrições genéricas — é por isso que o repositório de arquivos aparece como “M365 Drive-like, genérico”.

Decisões de projeto

Por que o desenho é assim

ADRs completos em docs/decisoes/
Nenhuma dessas decisões exige um fornecedor específico; todas são ferramentas livres e abertas.
DecisãoMotivo prático Custo aceitoReferência
Ingress na borda, em vez de expor o Service Um único lugar para TLS, rate limit, cabeçalhos de segurança e para o proxy de autenticação. O Service continua ClusterIP: se o Ingress cair, nada vira público. Mais uma camada para operar e uma dependência de controller no cluster. ADR 0001 · ingress.yaml
oauth2-proxy à frente do Service A aplicação não precisa implementar sessão/SSO para ficar atrás de autenticação; a allow list fica fora do código de negócio. Cookie extra, e o time precisa entender o fluxo de logout. oauth2-proxy.yaml · nota de privacidade
Secret montado read-only Credencial de um repositório de arquivos corporativo não pode ser escrita nem executada pelo processo; readOnly: true e volume tmpfs limitam o estrago de um RCE. Precisa de um mecanismo de rotação fora do pod (o arquivo modela o formato). secret-template.yaml
NetworkPolicy default-deny O pod da API fala com Mongo e com o conector; nada mais deveria conseguir. Converte “um pod comprometido alcança a rede toda” em lista explícita. Toda nova dependência exige uma liberação escrita e revisada. networkpolicy.yaml
Workers desacoplados da API Extração e OCR são lentos e comem CPU; a busca interativa precisa de p95 baixo. Separar permite escalar cada um pela sua métrica e reiniciar worker sem derrubar a UI. Eventual consistência: um documento publicado some na busca com atraso. ADR 0002 · deployment-worker.yaml
Publicar dados sintéticos, não o código original O código do cliente não pode ser aberto. Uma demonstração reprodutível mostra a mesma competência sem violar confidencialidade. Nada aqui prova performance em ambiente real — e a página diz isso. ADR 0003 · aviso sintético

      Privacidade e o que não está aqui

      Removido de propósito

      • Nomes de clientes, empregadores, marcas de empresas com as quais trabalhei e domínios corporativos.
      • URLs internas, endereços IP reais, nomes de arquivos reais e caminhos de pastas reais.
      • CNPJ, CPF, inscrição estadual, chave de acesso de documento fiscal, qualquer número que passe em dígito verificador.
      • Credenciais, tokens, chaves privadas, certificados, cookies de sessão.
      • Conteúdo de documentos fiscais reais e qualquer dado pessoal de terceiros.
      • Telemetria real, nomes de times, nomes de pessoas e tickets internos.

      Substituído por

      • Identificadores prefixados (EMP-DEMO-…, DOC-FISCAL-SINT-…, NF-DEMO-…) que não passam em nenhuma validação de documento fiscal.
      • Um repositório de arquivos descrito de forma genérica (“M365 Drive-like”), com caminhos de exemplo sob /Demonstracao-Fiscal/.
      • Hosts .example.com e um namespace automacao-demo.
      • Traces, logs, métricas e incidentes gerados por script, com a fórmula registrada.
      • Um verificador automático (tools/leak_check.py) que roda no CI e barra regressão de privacidade.

      English summary

      What this is

      A static, self-contained demonstration of a fiscal document automation product: search and retrieval of tax documents stored in a corporate file repository, an extraction pipeline (discovery → ingestion → extraction → schema validation → publication → human review), and the SRE layer around it (SLIs, error budget, burn-rate alerting, Kubernetes manifests, GitOps).

      The original customer code cannot be published, so this repository publishes the design plus synthetic data. Companies, documents, traces, logs, metrics and incidents are generated by tools/gen_data.py from a fixed seed (20260124) and are reproducible byte for byte. No real client, employer, domain, IP address, tax identifier or credential appears anywhere; a CI check (tools/leak_check.py) enforces that.

      Stack shown: React + FastAPI + MongoDB in the original case, evolving to containers, managed Kubernetes, an ingress plus oauth2-proxy at the edge, decoupled extraction workers, OpenTelemetry with Prometheus, Alertmanager, Loki, Tempo and Grafana, and Argo CD for GitOps. Everything is open source; the page itself has zero third-party dependencies and works offline.

      The demo runs without authentication. Scale figures are labelled as an illustrative order of magnitude, never measurements. If you want to talk about the real case, the links below are the way to reach me.
